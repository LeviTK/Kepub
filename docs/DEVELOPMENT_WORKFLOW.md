# 当前开发流程

本文件规定任务如何进入开发、审查和交付，不表示任何待办已经获准编码。功能顺序见 [开发计划 §0.2](DEVELOPMENT_PLAN.md#02-最小制书闭环优先八域三级拆分与交付顺序)，行为以 [CLI 契约](CLI_CONTRACT.md)为准，安全不变量以根与模块 AGENTS 为准。历史审查、旧模型与旧调度指令仅保留执行归属；当前执行者、模型和授权范围在每批任务中明确，不从历史配置自动继承。

## 1. 一批任务的准入条件

开始编码前，在 Issue 中明确以下六项；缺失时先补计划，不猜测扩权：

1. **目标与非目标**：用户可观察结果、失败边界、此次不实现什么。一个模块可分多个可独立验收的 PR，不必按每条三级清单创建 PR。
2. **依赖与基线**：前置 Issue 的实际交付状态、base commit、目标分支；计划中存在不算依赖完成。
3. **契约**：新命令/schema、兼容性、预算、来源与错误含义；新能力先冻结版本化契约，不扩旧接口。
4. **风险与验证**：按下一节选级别，列合法正控、能拒绝错误实现的反例、真实 CLI/checker/平台要求。
5. **所有权**：编码者、独立审查者、协调/父验收者与主要文件范围；并行工作不得写同一文件或隐含等待未到达的输入。
6. **授权**：区分计划、编码、本地集成、push、PR、merge、关闭 Issue 和 release。已获明确授权不重复询问，未获授权不由 CI 或评论推导。

同一作者换提示词或角色不算独立审查。独立线程使用独立 checkout；已有合适线程优先复用。工具、模型不可用时报告阻塞或请求替代，不冒充执行、不擅自升级昂贵模型，不为多开 agent 而拆任务。

## 2. 按风险选择验证，不按改动行数

混合改动按最高风险执行；契约或验收标准改变不能因为文件是 Markdown 就降级。下表是最低要求，不覆盖或削弱根 AGENTS、冻结反例和具体批次附加门槛。

| 类别 | 判断依据 | 必需检查 |
|---|---|---|
| 文档/指导 | 不改变行为契约、构建或测试含义 | 路径、链接、事实、规则一致性；涉及 skill 才核元数据与实际加载；无需产品全套 |
| 仅测试 | 产品、构建与依赖未变 | 新/改测试普通与相关 race；回归旧红新绿；高风险断言必要时用突变验证判别力；核已有产品证据适用性 |
| 局部产品 | 不改变共享来源、事务或门禁 | 受影响普通测试、公开接口正反例、相关真实 CLI；并发路径加 race；独立审查与父验收 |
| 共享核心/高风险 | 来源、XML 字节、identity、URL、预算、事务、恢复、安全边界或共享依赖 | 定向正反例与 focused race、旧 schema/冻结回归、相关真实 CLI/checker；完整普通→race→vet；按风险选择组合矩阵与父端集成检查 |
| CI/构建/验证工具 | 改变怎么产生或判断证据 | 语法/配置检查及工具自身正反例；核命令失败、超时、缺工具与输出绑定；按影响范围重跑产品检查，不归为纯文档 |

共享批次保持以下顺序；可以使用 CI 已声明的并发/内存约束，但在收据中写实际参数：

```sh
go test -count=1 -timeout=30m ./...
go test -race -count=1 -timeout=30m ./...
go vet ./...
```

新测试优先通过公开接口检查行为，不锁私有字段和调用顺序。永久回归要有独立期望；验证用 scratch probe/mutant 不必全部进入仓库。原冻结探针与失败日志不改弱；旧断言确已被授权新契约取代时单列校准理由，不能改写成“旧测试全绿”。UI 外观须实际渲染检查，交互须实际操作；Mac、真实断电和无障碍要求按任务单列，Linux CI 不替代。

## 3. 从编码到主线的检查点

| 状态 | 进入/退出条件 |
|---|---|
| Backlog | 已记录需求；不代表授权编码 |
| Ready | 六项准入信息齐全、依赖满足且本批开发已获授权 |
| Developing | 最小增量；必要重构与行为变化分开；修复先证实旧树反例 |
| In review | 自测完成，输入固定；提交交接收据；审查者只读检查固定树 |
| Changes requested / Blocked | 实证缺陷、必需工具/证据缺失或范围待决；说明恢复条件，保留原执行 |
| Accepted locally | 独立结论与父验收均覆盖本次固定输入及范围；不是远端交付 |
| Merged | 获授权合并到 main；精确记录 merge SHA 和复测评估；评估要求的检查未结束时不得写交付检查完成 |
| Done | 适用验收、合并后检查与范围核对完成；按授权关闭对应 Issue，发行另计 |

状态写在 Issue/PR 当前摘要中即可，不强制为每个状态建立标签。沿用 `type:*`/`bug`/`enhancement`、`area:*`、必要 `status:*`；标签不替代 open/closed/merged。阶段通过不自动授权下一批。

### 固定输入与修复循环

- 核 Git 状态、base/HEAD/tree/upstream；区分本地 main、origin/main 和编码工作树。不要切换、stash、清理或覆盖其他人的修改与证据。
- 优先使用可获取的精确 commit；未推送工作跨 Orb 传递 bundle/文件并核 hash、prerequisite、目标 tree。消息中的 SHA 不会传送代码。
- 以 [交接与验收收据](templates/CHANGE_RECEIPT.md)记录输入、测试、结论和限制。tracked dirty 结果标记为工作树执行，不能冒称固定提交验证。
- 审查期间不修改受审树。作者可在自己的树修复并产生新 fixed；原检查自然结束，除明确的挂死等情况外不取消重跑。
- reviewer 给出具体触发、期望/实际结果和依据；假设、测试工具错误、范围外发现分别记录。已证缺陷优先处理，不用总 PASS 抵消。
- 新 fixed 重放相关原反例并审查增量；父端核内容保留与交互。相同文件、不同 merge 身份不能仅凭祖先关系猜测内容相同。

## 4. 证据复用的边界

**复用执行结果，不迁移批准。** 即使产品字节完全相同，新 fixed 仍须有针对该身份的适用性结论及父验收；不能写“本轮全套已跑”。

复用前，收据必须列出：

1. 旧输入、旧命令、执行者、日志及适用范围。
2. 新旧全树路径集合与 `(mode,type,blob)` 比较；逐项解释差异，不能只比 Go 文件。
3. 构建配置、依赖、生成器、测试夹具、运行参数、checker 与相关环境是否变化。
4. 本轮新增检查与仍未验证的部分。

纯指导变更须检查规则与实现一致；仅测试变更须实际执行新测试并核其判别力。产品或验证环境变化，重跑受影响证据；无法证明适用时，不复用。作者、reviewer、父、CI 各自的执行来源必须保留，不能把借用结果写成独立重跑。

父端组合验收仍必需；它可以引用已核准的相同内容全仓结果，并独立执行新增交互/组合控制，不要求各角色机械复制每一条长命令。具体批次要求独立全仓或实机时照常执行，不能凭通用复用规则豁免。

## 5. CI、日志与远端交付

现有 [Linux CI](../.github/workflows/ci.yml)保留 PR 自动检查，绑定准确 PR head；**main push/合并不自动触发全套 CI**。先评估复测必要性，再通过 `workflow_dispatch` 选择分支或 tag，填写必填 `reason`（评估理由与关联 Issue/PR）。手动执行绑定事件的 `github.sha`，输入日志记录 ref、理由和实际 commit/tree；分支后续移动不改变该次检出的输入。手动入口须先进入默认分支才可在 GitHub 使用。

合并评估由协调/父验收者在 PR 收尾记录：merge SHA、变更风险、PR head 与合并树的差异、可复用证据和环境、结论及理由。不是只按文件后缀自动跳过：

| 情况 | 主线复测决策 |
|---|---|
| 纯说明/指导且不改变行为或检查含义 | 核文档和规则一致性，通常不重跑产品 CI |
| PR 已通过，合并产品/构建/依赖/夹具内容等同且环境适用 | 明确复用准确输入的证据，可不重复全套；不称主线新跑 PASS |
| base 漂移、冲突解决、组合内容变化，或存在未覆盖交互 | 做影响分析；必要的定向/组合检查必须执行，无法证明覆盖时运行全套 |
| 共享核心、构建/依赖/CI 改动缺少适用证据，或发行候选有验证缺口 | 补足必需完整验证；需要 GitHub runner 证据时手动触发全套，不因成本豁免 |

评估结论分为“复用/无需重复”“需定向复测”“需全套 CI”“阻塞待核”，写明执行位置与结果。不能默认勾选通过或仅以“省时间”为跳过理由；保留原共享批次门禁。当前手动 workflow 只执行全套，不提供假装执行的 skip 模式；定向检查在 Orb 中按准确输入记录。未获必要远端执行授权时先报告阻塞，不自动 dispatch。

CI 记录身份/工具版本，依序执行普通、race、vet，构建普通/race CLI并上传日志。构建 race CLI 不等于已使用该二进制执行每项真实 CLI 场景。PR head 检查不自动证明最新 main 的合并交互；需主线复测时核实际 merge SHA 与手动运行 SHA，不能把更晚的 main 当该合并身份。

现有自动化继续使用，不新增平行 CI。Orb 记录命令时开启 `pipefail`，不能让 `tee` 掩盖测试退出码；长任务追踪原 PID，不为刷新输出重启。以下为可执行的记录示例（日志放临时目录，不作为已完成执行证据）：

```bash
set -euo pipefail
results=$(mktemp -d "${TMPDIR:-/tmp}/kepub-check.XXXXXX")
{
  date -u +%FT%TZ
  git rev-parse HEAD HEAD^{tree}
  git status --short --branch
  go version
} > "$results/input.log" 2>&1
printf '%s\n' 'go test -count=1 -timeout=30m ./...' > "$results/command.txt"
rc=0
go test -count=1 -timeout=30m ./... 2>&1 | tee "$results/test.log" || rc=$?
printf '%s\n' "$rc" > "$results/exit.txt"
date -u +%FT%TZ > "$results/completed.txt"
(cd "$results" && sha256sum input.log command.txt test.log exit.txt completed.txt > SHA256SUMS)
printf 'results=%s exit=%s\n' "$results" "$rc"
exit "$rc"
```

每次执行分别记录命令、退出码、PASS/FAIL/SKIP、超时/工具错误、实际输入及日志 hash。不从包装脚本 exit0 推断所有测试成功。checksum 证明文件完整性，不证明测试覆盖或审查批准。

CI artifact 目前保留14天；关闭批次前将可公开的必要验收收据与证据索引持久保存，不能把短期下载链接当长期证据。私有书、凭据、敏感路径与原始日志不上传公共 Issue/PR；需要保留的私有证据使用获授权的私有位置，并明确公开部分的验证限制。

获授权创建/交付 PR 后，订阅评论/审查和准确 head SHA 的 CI；head 改变时更新相应 CI 跟踪。主线只有评估决定运行 CI 后才跟踪对应输入，不对预期无运行的合并反复等待或重试。通知是待核事实，不授权修复后 push、合并或发布。没有检查不等于通过；一次 job 成功也不等于全部门禁通过。

分支保护、required checks、审批策略是远端设置，须单独获准并实际核验；流程文档不能代替 GitHub 强制门禁。本次流程维护不修改远端设置、不自动发布或关闭 Issue。

## 6. 进度与收尾

在范围变化、进入审查、发现阻塞、验收和交付时更新，不逐条播报工具操作。报告四项：当前阶段/固定输入、已完成与剩余验收、阻塞与未测项、剩余时间区间及假设。没有实测依据时标低置信，不按 agent 数量线性缩短估算，不把创建 Issue 计为实现进度。

关闭前核原验收清单。剩余范围可拆子 Issue，写明原项哪些已交付、哪些转移及原因；不能靠拆单悄悄缩小承诺。父项需满足原范围才关闭，部分完成保持开放。合并、关闭与发行各自使用对应授权。

维护稳定根因时，更新最窄 AGENTS 与 [开发注意事项](DEVELOPMENT_NOTES.md)的“规则→失效模式→回归入口”；本文件只维护流程，不复制全部产品不变量或历史日志。
